# 国标交通协议解析平台 · 设计方案 v0.1

> 首个落地协议：**GB/T 32960.3（新能源汽车国标 远程监控通信协议）**
> 产品形态：Web 页面 + REST API；核心解析能力为独立可复用模块
> 参考：https://jttools.smallchi.cn （JTTools，支持 808/809/1078/19056/905/苏标/粤标）

---

## 1. 目标与范围

### 1.1 要解决什么

输入一段完整的 16 进制报文，输出两样东西：

1. **报文类型中文名**（如「车辆登录」「实时信息上报-整车数据」），逐层定位到帧 → 数据单元 → 子包 → 字段；
2. **明文解析结果**：字段中文名 + 工程值 + 单位/枚举中文（如 `车速: 35.6 km/h`、`车辆状态: 01 → 启动态`），同时保留每个字段对应的**原始 hex 片段**方便人工核对。

### 1.2 核心设计目标

| 目标 | 含义 |
|---|---|
| 顺序化输出 | 输出为**单流节点列表**：报文头 → 数据体（循环子块/字段树） → 校验码，按协议字节顺序；不再分「报文头/数据体」两段 |
| 错误友好 | 校验错、长度不符、未知命令字、未知枚举值都要**明确报出位置**（issues），而不是解析崩溃；未匹配场景（协议未登记/未知命令/拆帧失败）统一把剩余字节打包为「未知报文」节点展示报文原文并停止该层后续解析 |
| 可扩展 | 新增报文类型 = 新增/修改一份描述文件；新增协议 = 写一个 FrameAdapter（代码）+ 一组描述文件 |
| 可复用 | 解析引擎本身不依赖 Spring/网络，可被其他 Java 工程直接引用 |

### 1.3 明确不做（首期）

- 不做报文的**组包/编码**（hex 明文 → 二进制），只做解析；接口预留 `mode: encode` 的可能性。
- 不做加密数据体的实际解密（32960 加密方式字段解析出来，解密器做成可插拔钩子，首期支持「未加密 0x01」。
- 不做数据库（理由见 §5）。

## 2. 关键设计决策

### D1 一半写代码，一半写配置（采纳你的意见）

「协议怎么拆包」和「报文里每个字段是什么」分开：

- **帧层（代码）**：每种协议的起始符、包头布局、长度计算、校验算法（BCC/CRC/异或）、转义规则（808 的 0x7D 转义之类）差异极大且长期稳定，用代码实现为 `FrameAdapter`。这层不做配置，保证可靠可测试。
- **字段层（配置）**：每种报文的数据体字段列表（名称、类型、长度、缩放、枚举中文、循环块……）用 **YAML 描述文件** 定义，随代码进 Git。协议升级（如 32960 有新版修订、各省私有扩展）主要改这里。

### D2 配置不用数据库

见 §5 的专题分析。结论：完全可行且首期无需数据库。

### D3 内置字段解码器 + 自定义解码器兜底

配置 DSL 不追求"表达一切"。90% 的字段走内置类型；特殊逻辑（如 32960 报警数据的位表、厂家私有加密）提供一个 `CustomDecoder` 注册接口，用 Java 写，按 `协议名/命令字/字段路径` 挂载。避免 DSL 无限膨胀。

### D4 支持多版本共存

协议描述文件带 `version` 维度（如 `32960.3-2016`、预留 `32960.3-2025`）。同一个命令字在不同版本下映射到不同字段集，靠版本选择器解决；帧层若版本间差异大，`FrameAdapter` 内部按版本分支。

### D5 厂商扩展 = 独立完整配置（当前不做 overlay）

- 厂商配置是一份**完整的独立描述文件**（`<版本>/<厂商>.yaml`），结构与国标文件完全一致；选择厂商时直接加载这一份，不与国标合并。
- 多个厂商 = 多份文件；改国标后需要手动同步各厂商文件。这是为「配置简单、无合并歧义」接受的成本。
- 帧层完全复用：一个 `32960FrameAdapter` 服务国标 + 全部厂商，不写第二份拆包/校验代码。
- CustomDecoder 按字段路径注册，厂商可独立覆盖解码逻辑。

### D6 轻量原则

- 定位是「即开即用的解析工具」：启动快、代码少、可读性优先，**不做基建**。
- 单 Maven 模块（不拆 multimodule）；依赖只留 `spring-boot-starter-web`，不引 Lombok/MyBatis/Hutool 等重件。
- 前端零构建：Vue 3 本地 vendor 引入，无 npm/Vite/Node 工程链。
- 明确不做：插件 jar 热加载、DSL 解释器、标准 PDF 解析器、用户/权限体系。CustomDecoder 是普通接口 + Spring 注册即可，**不做成插件系统**。

## 3. 总体架构

```
┌──────────────────────────────────────────────┐
│ web/  Vue3 单页（粘贴框+协议/厂商下拉）        │  ← 零构建，本地 vue.global.js
├──────────────────────────────────────────────┤
│ REST API  /api/parse  /api/protocols         │  ← Spring Boot（现有工程）
├──────────────────────────────────────────────┤
│ jtt-core（纯 Java，无 Spring 依赖）           │
│  ├ HexCodec        hex 归一化（扫空格/回车）  │
│  ├ FrameAdapter(SPI) 各协议帧层，代码实现      │
│  │   └─ 32960FrameAdapter 起始/长度/校验/加密  │
│  ├ DescriptorRegistry 从 yaml 加载报文描述    │
│  ├ Engine          依据描述文件逐字段解析      │
│  ├ FieldCodec 商 内置解码器库（BCD/整型/…）    │
│  ├ CustomDecoder(SPI) 特殊逻辑钩子            │
│  └ Result/Issue    解析结果树 + 问题清单      │
├──────────────────────────────────────────────┤
│ protocols/gc-32960/                           │
│     ├ <version>.yaml  命令码 → body / subtype（单文件嵌套） │
│     ├ <版本>/<厂商>.yaml  厂商完整配置（不做 overlay） │
│     └─ samples/       真实样例 + 期望输出（回归用例） │
└──────────────────────────────────────────────┘
```

模块建议：

- **单 Maven 模块**（包名不变 `com.xx`），仓库内分层：
  - `src/main/java/com/xx/jttprotocolparse/core/`：解析引擎，纯 Java、零 Spring 依赖，可独立复用；
  - `src/main/java/com/xx/jttprotocolparse/web/`：REST Controller 薄层（Spring Boot，依赖仅 starter-web）。
- **前端独立 `web/` 目录**：Vue 3，零构建（无 npm/Vite），一个 index.html + 少量 js。
- 后续协议（808/1078…）在 `protocols/` 平铺新目录即可上线，core 不改；厂商扩展追加 `<版本>/<厂商>.yaml`，引擎与 UI 均不感知。

> 建议顺手把 Spring Boot 3.0.2 升到 3.3+（2022 年的版本了），不影响本设计。

## 4. 解析流程

```
hex 字符串
  │ 1) 归一化：去空白/换行，校验奇偶长度、合法字符
  ▼
2) 协议判定：入参显式指定 protocol；未指定时按各 Adapter 的
   特征自动识别（32960 → 起始符 ##；808 → 0x7E；预留）
  ▼
3) FrameAdapter.parseFrame()
   - 按 32960 布局提取：起始符 / 命令字节 / 应答标志 /
     VIN(17) / 加密方式 / 数据单元长度(2B 大端)
   - 校验：总体报文长度 == 计算长度；校验码(BCC：起始符后到校验码前
     各字节异或) 是否相符 → 不符进 Issue，可配置"继续尽力解析"
  ▼
4) 一级路由：命令字节(+应答标志) → DescriptorRegistry 查 <version>.yaml
   - 指定厂商时直接加载该厂商的完整配置文件；同步先定 version
   - 普通报文直接得到 body；0x02 这类「一个命令、多种子报文」得到 subtype
  ▼
5) 二级路由 + 字段解析 Engine.parseBody()
   - stream 型数据体：可选的前置 body 字段（如采集时间 6B） + N×(数据类型 1B + 信息体)
     信息体没有长度字节，长度由该类型的字段定义决定；未知/未配置类型无法切包，剩余原样保留
     每条子包按「数据类型」查 subtype 定位其字段列表：
     定位/极值/报警/储能各有各的 body；厂商扩展报文也是新增 subtype 表项
   - 报警数据内部的自定义报警位等三级差异 → bit 表 / CustomDecoder
   - 逐字段执行 FieldCodec，记录 (value, rawHex, issue?)
  ▼
6) 输出 ParseResult
   ├── report: 报文中文全名（如「实时信息上报 · 整车数据」）
   ├── nodes:  单流节点列表：帧字段 → 字段树（label/value/unit/map/rawHex/children）→ 校验码收尾；
   │           未匹配时在对应位置放「未知报文」节点（展示报文原文）并停止后续解析
   └── issues: [{path, code, message}]  校验/长度/未知值问题（API 保留，页面不渲染）
```

## 5. 配置格式（YAML DSL）示意

> 以下是**结构示意**，具体字段长度/单位以标准正文核对后填入；关键字段均已核对标准时再落地。

清单 `protocols/protocols.yaml` 按「协议 → 版本 → 厂商」登记，解析时三者必须同时命中且文件存在，否则直接失败：

```yaml
protocols:
  gc-32960:
    label: GB/T 32960.3 新能源汽车国标
    versions:
      "2016":
        vendors:
          - breton
```

对应文件：`protocols/gc-32960/2016/breton.yaml`。

### 5.1 协议描述文件（`protocols/gc-32960/<版本>/<厂商>.yaml`）

命令码直接挂在根节点，`body` 内联；有子报文类型时用 `subtype` 嵌套。`body` 与 `subtype` 可以并存：

```yaml
protocol: gc-32960
version: "2016"
label: GB/T 32960.3 新能源汽车国标

"0x01":
  name: 车辆登录
  body:
    - label: 登录时间
      type: dec-time
    - label: 登录序号
      type: u2

"0x02":
  name: 实时信息上报
  body:                       # 子报文之前的固定前缀
    - label: 数据采集时间
      type: dec-time
  subtype:                    # 二级路由：数据类型 → 子报文
    "0x01":
      name: 整车数据
      body:
        - label: 车速
          type: u2
          scale: 0.1
          unit: km/h
    "0x02":
      name: 驱动电机数据     # 无 body：无法切包，会记 UNKNOWN_SUBTYPE

"0x03":
  name: 补发信息上报
  body:
    - label: 数据采集时间
      type: dec-time
  subtypeRef: "0x02"          # 复用 0x02 的子类型表

"0x06":
  name: 心跳                   # 无 body = 本应无数据体
```

有 `subtype` / `subtypeRef` 即视为 stream，不再写 `stream: true`；`subtype` 与 `subtypeRef` 互斥。

### 5.2 字段列表（body）

`body` 是字段列表，按顺序吃字节；分组标题复用命令名 / 子类型名。

- 字段统一使用 block 缩进（`- label:` 起头），不要混用 `{}` flow 写法。
- 字段不写 `id`：节点标识、issue path、`$` 引用统一使用 `label`。
- 被 `$` 引用的 label 只能包含字母/数字/中文（不要含空格或运算符）。
- `map` 是「原值 → 中文」映射，未命中时直接显示原值（如 `0x7F`）；`invalid` 是数值字段的特殊值映射（如 `0xFFFF` 异常），未命中回落到正常数值转换；同一字段 `map` 与 `invalid` 互斥，加载期校验直接失败。
- `bits` 是掩码型位表（只表达置位含义，如报警标志，未置位不显示）；位段取值（0/1 双态位、多位合成值如 bit1~2 的 TF卡状态）用 `segments`（start/width/values），两者互斥，加载期校验。
- `body` 与 `subtype` 并存时，body 只放定长子报文前缀字段（放 `length: rest` 会吞掉子报文区）。

```yaml
"0x01":
  name: 整车数据
  body:
    - label: 车辆状态
      type: u1
      map:
        "0x01": 启动态
        "0x02": 熄火
        "0x03": 其他状态
        "0xFE": 异常
        "0xFF": 无效
    - label: 车速
      type: u2
      scale: 0.1
      unit: km/h
    - label: 累计里程
      type: u4
      scale: 0.1
      unit: km
    # …… 按 2016 版标准补齐
```

### 5.3 DSL 内置能力清单（实现越晚不追加，仅此清单为有限集）

| 能力 | 用法示例 |
|---|---|
| 整型/有符号 | `type: u1/u2/u4/s1/s2`，byteOrder 默认大端 |
| BCD / ASCII / GBK | `type: bcd-time`（6B BCD）、`type: ascii/gbk, length: 16` |
| 十进制数值时间 | `type: dec-time`（6B：年 月 日 时 分 秒各一字节数值，如 `1A 0A 14 11 23 00` → `2026-10-20 17:35:00`） |
| 数值缩放/偏移/单位 | `scale: 0.1`、`offset: -1000`、`unit` |
| 枚举映射 | `map: {…}`，未命中直接显示原值；位表型用 `bits:` |
| 特殊值映射 | `invalid: {"0xFFFF": 异常}`：数值字段命中显示中文，未命中按 type 转换；与 `map` 互斥（加载期校验） |
| 位段映射 | `segments: [{start, width, values}]`：数值字段按位段合成值查表（如 bit1~2 的 0~3），未命中显示该段十进制值；段加 `label` 则以子节点行展示，无 label 的段以「；」拼接；与 `bits` 互斥（加载期校验） |
| 动态长度 | `length: "$驱动电机个数*14"` 引用前文字段（label）做乘积运算 |
| 循环块 | `type: group, count: "$驱动电机个数", fields: [...]`（驱动电机/储能子系统）|
| 条件字段 | `when: "version >= 2025"`（多版本差异）、`when: "flag == 3"` |
| 原样保留 | `type: raw`，厂家私有/未定义部分不动，提示"未解析" |
| 定长填充 | `pad: 0x00` 忽略 |

表达不了的 → `CustomDecoder` 钩子（Java，按字段路径注册）。

### 5.4 厂商配置（`protocols/gc-32960/<版本>/<厂商>.yaml`）

厂商文件是一份**完整独立配置**，结构与国标文件相同，不做 overlay。复制国标文件后按需修改：

```yaml
protocol: gc-32960
version: "2016"
label: GB/T 32960.3 新能源汽车国标   # 报文名前缀
vendor: XX汽车                        # 展示名（加载器优先使用它）

"0x02":
  name: 实时信息上报
  body:
    - { label: 数据采集时间, type: bcd-time }
  subtype:
    "0x01":                           # 国标子报文需要在本文件里完整复制
      name: 整车数据
      body:
        - { label: 车速, type: u2, scale: 0.1, unit: km/h }
        - { label: XX扩展字段, type: u1, map: { "0x00": 关闭, "0x01": 开启 } }
    "0x70":
      name: 扩展报文-充电诊断
      body:
        - { label: 数据时间, type: bcd-time }
        - { label: 扩展明细, type: raw, length: rest }
```

要点：

- 选择厂商时只读这一份文件，**不回落国标**；厂商没写的命令就是没有。
- 多个厂商 = 多份完整文件；改国标后需要手动同步。
- 已移除 `extend` / overlay 语法，厂商文件里不要写 `commands:` / `bodies:`。
- 输出报文名自动带厂商前缀：`GB/T 32960.3 新能源汽车国标 · XX汽车 · 实时信息上报`。
- 未指定 vendor 时走国标基准；`GET /api/protocols` 会列出各协议可用的 vendor 清单。

### 6.3 Web 页面（MVP）

`web/index.html` 单页：textarea（支持一次粘多条，空行分隔，对齐 JTTools 体验）+ 协议/版本/厂商下拉 + 「解析」按钮 + 结果树/表格 + 原始 hex 对照。

页面**单流渲染 `nodes`**（不再分「报文头/数据体」小节，也不渲染 issues 条；未匹配信息由「未知报文」节点承载），保持中性视觉。

前端用 **Vue 3 零构建**：不引 npm/Vite/Node 工程链，`web/vendor/vue.global.prod.js` 本地引入，一个 html + 两个 js 文件解决；组件需要时页面内直接写，等真的复杂到要工程化再上 Vite（符合"不要过度实现"）。

## 7. 不使用数据库的可行性分析

**结论：可行，且首期建议明确"零数据库"。**

1. **解析是无状态纯计算**：`hex in → 明文 out`，无持久化、无会话、无业务数据，天然不需要 DB。
2. **协议描述是只读配置**：YAML 是一等资产，Git 天然承担了版本化、diff、评审、回滚——这些正是大多数"配置入库"场景的真实诉求，反而更规范。
3. **加载机制**：启动时从两层加载——
   - 内置（classpath，随 jar 发布）；
   - 外置目录（`--protocols.dir=./protocols`），优先级高于内置，便于不改代码扩报文。
   - 可选热更新：`WatchService` 监听外置目录 + `POST /api/reload`。
4. **多实例部署**：把同一份外置描述目录挂给所有实例（本地盘同级文件）即天然一致，不需要共享存储。
5. **「在线配置协议」如果未来要做**：提交的自定义协议先落入内存 Registry（重启失效）+ 建议导出为 YAML 文件入 Git，仍无需 DB。
6. **什么时候才需要 DB**：要保存「解析历史 / 报文库 / 用量统计」时。首期用**JSONL 日志文件**即可留底；真到需要检索时，再加 SQLite / 普通库，且引擎本身无需重做。

> 原则：**引擎不依赖存储；存储是产品层的可选能力。**

## 8. 风险与取舍

| 风险/取舍 | 应对 |
|---|---|
| YAML DSL 表达力有限 | 内置类型清单收敛 + CustomDecoder 钩子兜底；不为特殊逻辑疯狂加语法 |
| 描述文件写错 = 解析错 | **每个报文必须配真实样例**（`samples/`）：报文 + 期望输出 JSON，CI 回归 |
| 新版/私有协议差异 | version 维度 + 厂商独立完整配置 + `raw` 字段 + CustomDecoder |
| 厂商文件重复维护 | 每厂商一份完整文件，改国标后手动同步；用 samples 回归兜底 |
| 加密数据解析不了 | 加密方式字段可解析并明确提示「已加密，不支持明文解析」 |
| 一次粘贴多条/分包 | 归一化按空行拆分逐条解析，失败的单条独立报 issue，不影响其他 |
